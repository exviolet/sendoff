# Sendoff Roadmap

> Долгоживущий документ. Источник правды по позиционированию, приоритетам и явным отказам. Обновляется по мере принятия решений в сессиях.

## Позиционирование

**Sendoff — prompt-first editor для быстрой формулировки LLM-промптов.** Возник из конкретной боли: маленький input в Claude Code + неудобный scroll в tmux при долгих сессиях.

**Не является:** pipeline-builder, knowledge base (Obsidian/Notion), code editor (VS Code/Vim).

**Целевой flow:** написал промпт в Sendoff → отправил в активную tmux pane (см. фичу #1) → продолжил в Claude Code.

### `oborchers/proqi` — ближайший сосед, найден 2026-09-05

Формулировка проблемы совпадает с нашей почти дословно: единственный input у агентского CLI,
черновик конфликтует с живой сессией, альтернативные формулировки расползаются по временным
файлам. Пришли к этому независимо — Sendoff существует с марта, proqi создан 23 августа.

**Проверено через GitHub API** (не пересказ README): создан 2026-08-23, `v0.7.0`, четыре
релиза за восемь дней, 13 звёзд, MIT, Rust, по 14 ассетов в релизе.

**Из README, в коде не проверялось:** Ratatui + SQLite на диске, доска «мыслей» вместо табов,
отправка через «verified protocol» Herdr плюс буфер обмена и JSON CLI, инбокс скриншотов на
macOS, явное «never invokes shells, injects keys».

| | Sendoff | proqi |
|---|---|---|
| Форма | GUI (Tauri + webview) | TUI (Ratatui) |
| Платформы | Linux | macOS + Linux |
| Хранилище | IndexedDB в webview | SQLite на диске |
| Цели отправки | tmux, Herdr, Orca | Herdr, буфер, JSON CLI |
| Модель документа | табы, workspace, группы | доска «мыслей» |
| Дистрибуция | 1 AppImage (+вечнозелёная копия) | 14 ассетов на релиз |

**Три факта, которые невыгодно смягчать.** Они отгружают быстрее (4 релиза за 8 дней против
наших 3 за месяц) и уже собрали мультиплатформенную дистрибуцию. У них есть канал, у нас нет:
13 звёзд за 12 дней — это пост на r/tui, а не качество кода; наш разрыв измеряет ровно
неначатую стадию C. И их «never invokes shells, injects keys» нацелено ровно в наш путь через
`tmux set-buffer` / `paste-buffer` / `send-keys` — после hardening'а v0.3.0 мы защищены не
хуже, но их позиция формулируется одной строкой, а наша абзацем, и в лобовом сравнении
короткая строка выигрывает.

### Herdr — не нишевая утилита, а экосистема

`herdrdev/herdr` — **35k звёзд**, «the runtime your coding agents live on». Вокруг сложился
обвес компаньонов: `herdrm` (654), `herdr-reviewr` (597), `herdr-file-viewer` (528),
`herdr-remote` (314), `herdr-mirror` (216). proqi — ещё один житель этой экосистемы.

**Sendoff технически в ней уже стоит и нигде об этом не заявлен.** Мы говорим с ней по
официальному CLI — `herdr agent prompt` и `herdr pane send-text`, заскоупленные валидаторами
в манифесте (`default.json`). То есть совместимость есть, видимости нет.

### Что решено НЕ делать

- **Не копировать доски, vim-навигацию и инбокс скриншотов.** Реактивная фичегонка за соседом
  — ровно тот scope creep, против которого написано позиционирование.
- **Не переписывать в TUI.** Sendoff существует ПОТОМУ ЧТО автор хотел выйти из терминала;
  TUI-композер это инверсия собственного позиционирования, а не ответ конкуренту.

### Открытые вопросы

- **Заявляться ли в экосистеме Herdr** как совместимый инструмент — главный кандидат в
  «площадки стадии C», которые до сих пор стояли абстракцией. Не решено.
- **Стоит ли документировать различие с proqi публично** (раздел в README) или оставить как
  есть. Пока не решено; преждевременно, пока обе стороны на 0.x.

### Что уже сделано

2026-09-04 автору proqi написан комментарий в его же треде на r/tui: общая боль, независимость
маршрутов, предложение сравнить решения, ссылка на Sendoff. **Первое конкретное действие
стадии C** — реактивное, не спланированное. Основная ценность не в ответе автора, а в читателях
треда. Ответа на момент записи нет. Если через несколько дней не будет — следующее касание
должно быть содержательным (issue про Herdr-протокол: что он даёт поверх CLI), а не социальным.

### Решения grill-сессии 2026-06-03 (tmux deep integration + tab UX)

- **Split-view отклонён** — дублирует существующую reference panel (`Ctrl+R`, уже side-by-side) и дрейфует в code-editor/IDE (анти-позиционирование). Заменён на #11: апгрейд reference panel до указания на живой таб.
- **tmux tab-binding (#9) биндит по имени `session:window`, НЕ по `@id`.** Window/pane `@id` эфемерны — ресетятся при рестарте tmux-сервера (ребут), поэтому persistent-привязка к `@id` протухает ровно как global-last (который сознательно НЕ персистится). Дескриптор `{session_name, window_name}` резолвится живьём в момент отправки; если окно не найдено → модалка + toast. Цена: давать агентским окнам стабильные имена (`tmux rename-window claude`).
  > **⚠️ ИСПРАВЛЕНО 2026-07-10 — это решение было НЕВЕРНЫМ и породило критический баг.** Имя окна **не уникально**: в agentic-флоу два окна `claude` — норма, а `.find(w => w.name === …)` брал первое → промпт улетал не тому агенту. Мотив («`@id` эфемерны») верен, вывод («значит биндим только по имени») — нет. **Актуально:** первичный ключ — `window_id` (`@N`), имя остаётся для отображения и как fallback. Резолв: (1) `@id` **И** имя совпали → точное попадание; (2) иначе по имени — ровно одно совпадение берём, **несколько → `ambiguous`**; (3) ноль → `not-found`. Сверка имени на шаге 1 защищает от переиспользования `@id` после рестарта сервера. **Инвариант: при неоднозначности НЕ угадывать** — переспросить (тост + bind-picker). Не откатывать к матчингу только по имени.
- **«Active pane» как тихий дефолт `Ctrl+Enter` уходит в #9.** Цепячка резолва — Explicit (tab-binding) → Last (global, in-memory) → Modal (fallback). «Active pane» остаётся лишь пунктом *внутри* модалки. В #8 `Ctrl+Enter` пока не трогается (чисто аддитивная фаза).
- **Persistence split (#9):** tab-binding → IndexedDB (переживает ребут); last-global-target → Zustand in-memory (протухает с сессией, персистить вредно).
- **Settings (#9):** два тумблера (`remember last globally` = on, `auto-bind on pick` = off) — захардкодить дефолтами, выносить в Settings-UI только если догфуд покажет потребность флипать. Не строить панель под пустоту.

## Терминальные таргеты + обратная связь (решения 2026-06-14, ревизия 2026-06-16)

**Herdr — candidate target (без кода, испытательный срок ~1 неделя).** Новый
мультиплексор для агентов с нормальным CLI/API: `pane list`, `pane read`,
`pane send-text`/`send-keys`/`run` — реальный кандидат во вторую реализацию рядом
с tmux. Решение: `TerminalTarget`-абстракцию **не строить заранее**. Пользователь
тестирует Herdr неделю; если приживётся в agent-workflow — абстракцию вводим **в
момент второй реализации**, не раньше (split-when-needed: извлечь интерфейс из
одного impl при добавлении второго дёшево). Если Herdr CLI окажется
tmux-совместимым — поддержка почти бесплатна.

> **Обновление 2026-07-01:** herdr-кандидат **вытеснен Orca ADE** (адоптирован,
> скриптовый CLI `orca-ide`, семантический слой сессий). Orca — сильнее как «вторая
> реализация» `TerminalTarget`. Herdr не тестировался. См. секцию «Orca ADE».

> **Обновление 2026-08-01: herdr вернулся и стал daily driver — вытеснение отменено.**
> Оба пользователя перешли на herdr; Orca оставлена для >3 проектов одновременно
> (причина — потребление ОЗУ, см. секцию «Сессия 2026-08-01»). Испытательный срок
> закрыт положительно, только по факту эксплуатации, а не тестами. `TerminalTarget`-
> абстракция, которую эта секция откладывала «до второй реализации», **извлекается
> сейчас** — реализаций стало три. Спек: [tasks/15-herdr-target.md](../tasks/15-herdr-target.md).

**2a (Capture bound pane → Reference) — ЗАКРЫТО (spike 2026-06-16).** Голый
zero-code тест `tmux capture-pane -S -200 -p` на реальном TUI-агенте (Claude Code)
показал: capture возвращает **весь отрендеренный экран TUI** (tool-calls, глифы
`●`/`※`/рамки, статусбар, прошлые промпты), а не чистый последний ответ. Чтобы
вытащить ответ — нужен хрупкий per-agent парсинг (Claude Code/Codex/pi рендерят
по-разному). Авто-capture **проигрывает** ручному Ctrl+R/manual paste ровно на
целевых таргетах (TUI-агенты). Herdr `pane read` это **не спасает** — читает тот
же отрендеренный пейн (проблема в TUI-репейнте, не в backend). Цена выяснения: 0
строк кода, 0 новых permission, 0 расширения threat model. Permission
`capture-pane` **не вводим**.

**sendoff-cli / sendoff-agent — НЕ строим (решение 2026-06-16).**
- **LLM-powered CLI** (`rewrite file.txt --preset formal`, provider abstraction,
  API-ключи, сеть) — out of scope. Реально шарит с GUI только `assemblePrompt()` +
  тип `PromptTemplate` (~10 строк + дата); ради этого `@sendoff/core` / монорепо —
  инфраструктура без жильцов. Провайдер-слой — net-new, не «вынесли общее».
- **sendoff-agent** (`send`/`list-targets`/`capture` как отдельный бинарь) —
  `send`/`list-targets` GUI уже делает in-process через `tauri-plugin-shell`
  (бинарь = дублирование через границу процесса без потребителя); `capture` —
  единственное новое, провалило spike выше. Жильца на отдельный бинарь нет.

GUI остаётся clipboard/local/terminal-agent oriented: без backend, без API-ключей,

## Orca ADE — адопция и Sendoff↔Orca интеграция (2026-07-01)

Пользователь установил **Orca ADE** (`stablyai/orca`, MIT): agent-development
environment — параллельные CLI-агенты в изолированных git-worktree, встроенные
терминалы Ghostty-класса, семантический слой сессий агентов, скриптовый `orca-ide`
CLI. **На испытательном сроке** (плейбук herdr). Разобрали, чем Orca является для
Sendoff, и спроектировали интеграцию.

### Ключевой вывод: Orca комплементарен, НЕ заменяет Sendoff

Orca = **мультиплексор/раннер агентов** (замена tmux + herdr для агентской работы),
но **у него нет своей prompt-поверхности** — открываешь тот же Claude Code / Codex в
его тесном TUI, просто в Orca-окне. Значит боль «маленький input» (ядро Sendoff)
**остаётся**. Sendoff встаёт поверх Orca как **companion**: комфортный ввод + умная
отправка, которой у голого `orca-ide` нет. Роль заточена, вопрос «переживёт ли
Sendoff Orca» закрыт — **да, комплементарно**.

### Спайк-доказательства (живьём, `orca-ide`)

- **`terminal send` — сырой `\n` = Enter** (ранняя отправка, как tmux). Обёртка в
  bracketed-paste (`\e[200~…\e[201~`) → многострочник держится одним буфером,
  `--enter` шлёт разом. Send feasible, переиспользует bracketed-логику `useTmuxSend`.
- **`terminal read` — сырой TUI-рендер** (PUA-глифы, box-draw, спиннер, scrollback).
  Тупик для чтения ответа агента, как tmux `capture-pane` (спайк 2a).
- **`worktree ps` — СТРУКТУРНЫЙ семантический слой:** `agentType`, `state`, чистые
  `prompt` / `toolName` / **`lastAssistantMessage`** (проверено: haiku-агент отдал
  чистый текст ответа, ноль рендер-шума). **Это ОТМЕНЯЕТ вывод спайка 2a для Orca:**
  output-направление (боль B) больше не тупик — Orca сам делает per-agent парсинг.
- **`terminal wait --for tui-idle`** — работает (`satisfied: true`).

### Решения

- **Интеграция в 2 фазы:**
  - **Phase 1 — Send (боль A):** `Ctrl+Enter` → bracketed-промпт в выбранного
    Orca-агента. Без новых клавиш (дескриптор привязки получает тег `source`).
    Target-цепочка переиспользует #9 (Explicit→Active→Modal); MVP — per-tab привязка
    через picker + Explicit→Modal, «Active-agent» дефолт best-effort (гейт — семантика
    `isActive`, picker — надёжный fallback). **Orca-only MVP**, tmux-путь не трогаем.
    Спек: [tasks/11-orca-send.md](../tasks/11-orca-send.md).
  - **Phase 2 — Reference-read (боль B): parked / next.** Reference panel получает
    `orca-agent`-режим — зеркалит `lastAssistantMessage`, рефреш петлёй
    send→`wait tui-idle`→`ps`. **Не stub-им детально, пока не станет active.**
- **Permission — Policy B (scoped, НЕ `args:true`):** только `terminal send`,
  `terminal list`, `worktree ps`, `terminal wait`. Блок: `computer` (десктоп),
  `terminal create --command` (спавн процессов), `worktree create/rm`, browser,
  automations. `args:true` молча выдал бы desktop-control + произвольные процессы. См.
  CLAUDE.md Safety Rails.
- **Reference panel — tab-режим (#11) под нож.** Сомнение по #11 = «непривычная»
  реализация (pencil A/B-swap: карандаш тихо перепривязывал панель) + слабый жилец
  (кто держит требования в отдельном Sendoff-табе?). orca-agent-источник обходит оба
  (read-only внешние данные, swap не нужен). Панель = `scratch | orca-agent`,
  tab-режим (ветка web `70d9f6c`) выпилить, оставить донором переиспользуемых кусков
  (source-picker, read-only body, insert).
- **herdr вытеснен.** Orca = «herdr, но семантический + скриптовый» — это и есть та
  «вторая реализация» `TerminalTarget`, которую ждала секция «Терминальные таргеты».
  Абстракцию извлекаем из двух impl (tmux+orca) при унификации picker'а — **отложено
  до решения судьбы tmux**.
  > **2026-08-01 — неверно, отменено.** «Herdr, но семантический» оказалось неточным:
  > у herdr **тоже** есть семантический слой (`agent list` с `agent_status`), причём
  > одним вызовом вместо джоина двух. Ошибка была в том, что herdr так и не
  > протестировали — вывод сделан по сравнению документации, а не спайком.
- **tmux fate — не решено** (Orca на испытательном). Унификацию picker'а не строим,
  пока не ясно, угасает ли tmux для агентов.
  > **2026-08-01 — решено: tmux остаётся, все три таргета живут.** Унификация picker'а
  > и `TerminalTarget` — фазы A/C в [tasks/15](../tasks/15-herdr-target.md).

### Salvage: capture-as-input в Orca стал ближе

`worktree ps` — для агентов; но `terminal read` по **не-TUI** шеллу (build/test/

### Ревизия local-first (реформулировано, не отменено)

Автор оспорил local-first как догму: «мы же запускаем CC/codex — они сетевые, зачем сковывать руки?».
Разрез на две вещи под одним словом:
- **Продуктовая догма** («Sendoff никогда не в сеть/облако») — **снята.** Произвольна: Sendoff
  существует, чтобы кормить сетевые CC/codex/orca; офлайн им никто не пользуется.
- **Security-постура Tauri** («webview не делает произвольных сетевых вызовов / не спавнит процессы») —
  **сохранена, и это НЕ произвол.** У Sendoff `fs:scope-home-recursive` + write; home-read + сетевой
  egress = реальная поверхность утечки (`web/` тянется submodule'ом, не аудируется построчно). Широкий
  FS безопасен *именно потому*, что нет egress. Это в исключении «security — YAGNI отступает».

Формулировка: `local-first (догма)` → **`редактор держит границу no-network-egress; сетевое/AI живёт
в отдельном companion-продукте за узкой opt-in границей`**. Отражено в CLAUDE.md Safety Rails.

### AI-ассистент промптинга — брат-продукт (Triage, НЕ адоптировано)

Из брейндампа: «Sendoff помогает *составлять* промпты, имея контекст о проекте» (3 контекстных вопроса
как NotebookLM, memory-провайдер типа Hindsight/Hermes, RAG). Разрешение противоречия — **это другой
продукт, тесно связанный с Sendoff** (вывод самого автора), а не фича редактора.
- **Редактор-scope (можно, локально):** prompt-quality тулинг — структура/скаффолды/императивные
  чек-листы («расплывчатая фантазия → конкретное тех-требование»), продолжает `trigger phrases` (`Ctrl+K`).
- **Ассистент-scope (брат-продукт):** LLM-генерация промптов, RAG, память проекта — сеть + ключи +
  индекс = три red flag редактора (no-egress граница, не knowledge base). Отдельный companion.

**Статус: Triage.** Не проектируем, не даём течь в scope редактора. Дешёвая локальная альтернатива боли
«в длинных сессиях теряюсь / забываю решения»: локальный decisions/context-лог рядом с промптами (без
RAG/сети). Проверить, не решает ли он 80% боли, ПЕРЕД тем как строить retrieval.

### agent-hooks как back-channel — research-нота под брат-продукт (НЕ начинаем)

Наблюдение автора: Orca/herdr используют per-agent hook-скрипты (`~/.orca/agent-hooks/claude-hook.sh`,
`codex-hook.sh`, …) для прямого взаимодействия с агентами. **Ключевой инсайт:** именно так Orca получает
чистый `lastAssistantMessage`/`tui-idle` в `worktree ps` — через хуки, а не TUI-скрейп. То есть hooks —
**правильный примитив для back-channel**, в отличие от TUI-скрейпа (тупик спайков 2a/2b) и от
Orca-специфичного `worktree ps` (лок на Orca). Свои хуки дали бы orchestrator-независимый структурный
сигнал от ЛЮБОГО агента.

**Но это НЕ editor-фича, по трём причинам:**
1. **Дрейф в оркестратор.** Чтение состояния/ответов агента = слой Orca/herdr/tmux-CAO, который Sendoff
   *дополняет, не заменяет*. Подтверждено статьёй [nahornyi.ai про tmux-оркестрацию](https://nahornyi.ai/ru/news/tmux-cli-multi-agent-orchestration-pattern):
   она вся про *роутинг* агентов, но НЕ трогает *составление* промпта — вот зазор Sendoff.
2. **Новая security-поверхность = ломает границу редактора.** Хуки требуют: (a) Sendoff ПИШЕТ в конфиги
   чужих инструментов (`~/.claude/settings.json` hooks, codex-конфиг); (b) хук зовёт *обратно* → Sendoff
   ДОЛЖЕН слушать (localhost socket/pipe) = listener, ровно то, что no-egress граница исключает. → Место
   хуков — в брат-продукте (там и так сеть/ключи).
3. **Коллизия с Orca.** Когда оркестратор есть, он уже *владеет* хуками агента; Sendoff должен *потреблять
   его данные* (`worktree ps`), не ставить конкурирующие хуки. Уникальная ценность хуков — только для
   НЕ-оркестрируемого пути (голый агент в tmux).

**Диспозиция:** research-нота под брат-продукт (вероятный субстрат его read-side для любого агента).

## Сессия 2026-08-01 — Herdr адоптирован, `TerminalTarget` извлекается

Точка входа: оба пользователя (автор + друг) перешли на **herdr** и просят поддержку.
Herdr — не гипотеза: сессия велась внутри него.

### Почему herdr, а не «ещё один мультиплексор»

Рабочая модель автора: **≤3 проектов одновременно → herdr; >3 → Orca.** Разделение по
ресурсам, а не по фичам: Orca ест 2–3 ГБ ОЗУ уже на одном проекте с 2–3 агентами, herdr
на том же профиле — нет. То есть Orca не «хуже», она дороже, и платить за неё имеет
смысл, когда параллелизм реально большой.

### Спайк (live, herdr 0.7.5, protocol 17)

- **`herdr agent list` отдаёт готовый семантический JSON одним вызовом** — `pane_id`,
  `agent`, `agent_status` (idle/working/blocked/done), `cwd`, `focused`, `terminal_id`.
  Orca требует джоина `worktree ps` + `terminal list`, tmux — парсинга. Herdr дешевле обоих.
- **`herdr agent prompt <pane> <text>`** — first-class отправка промпта. Ни bracketed-
  paste руками, ни settle-таймера: и то и другое CLI делает сам. Это устраняет самый
  хрупкий кусок обоих существующих путей.
- **`pane_id` персистится** в `session.json` и переживает рестарт сервера и ребут —
  чего не умеют ни tmux `@id`, ни orca `term_…`. Первая привязка, которая не протухает.
- **НО номера панелей переиспользуются** → инвариант «сверять второй признак и при
  неоднозначности переспрашивать» (баг 2026-07-10) применяется в полную силу: резолв
  по `pane_id` **и** паре лейблов, лейблы не уникальны (две вкладки `codex` в одном
  workspace у автора прямо сейчас).
- **Read-стороны у herdr нет.** В `AgentInfo` нет аналога `lastAssistantMessage`; есть
  только `agent read` = тот же TUI-рендер, что провалил спайк 2a (2026-06-16).
  **Следствие: зеркало ответа агента (боль B, Phase 2 Orca) остаётся orca-only.**
  Herdr закрывает боль A (send) — и закрывает лучше всех.

### Решения (приняты автором)

1. **Все три таргета живут** → `TerminalTarget` извлекается. Секция «Терминальные
   таргеты» ждала абстракцию «в момент второй реализации», унификация picker'а была
   отложена «до решения судьбы tmux» — обе отложки сняты: реализаций три, tmux остаётся.
2. **Таргет herdr — только агентские панели** (`agent list`), не голые шеллы. Совпадает
   с orca-моделью; tmux-модель «шлём в любой pane» остаётся у tmux.
3. **Один пикер с секциями** (herdr → orca → tmux) вместо трёх, на `usePickerModal` из
   #9 с плоским курсором сквозь секции (образец — `GlobalSearchPanel`).
4. **Привязка схлопывается в одно поле** `Tab.binding` (дискриминированное объединение
   по `source`). Легаси `tmuxBinding`/`orcaBinding` читаются `normalizeTab` — не миграция
   данных, а нормализация на чтении; bump версии БД не нужен, привязки друга целы.
5. **Permission — Policy B, как у `orca-ide`.** `args:true` для `herdr` запрещён
   категорически: в одном бинаре `pane run` (произвольный процесс), `pane split/close`,
   `tab/workspace create/close`, `session stop`, `server stop`, `config`, `update`,
   `integration install`. Разрешены 5 форм: `agent list`, `workspace list`, `tab list`,
   `agent prompt`, `pane send-text`.

### Порядок фаз изменён: B вперёд A (решение автора)

Спек задумывал A (абстракция) → B (herdr) → C (единый пикер). Автор выбрал **начать с B**:
herdr нужен в бою сразу, а фаза A даёт нулевой видимый выигрыш при ненулевом риске на
daily-driver-пути отправки. **Цена принята осознанно:** herdr встал третьей копией
orca-паттерна. Фаза B отгружена и подтверждена живым прогоном (web merge `c2a134c`).

Что это значит для будущих A/C: реализованный herdr-путь **проще** двух других — у herdr
нет флага `--json` (вывод и так JSON, лишний флаг роняет команду), не нужна ручная
bracketed-paste обёртка и settle-таймер (`agent prompt` первоклассный, сабмитит сам —
подтверждено живьём), а `submit=false` идёт отдельной командой `pane send-text`.
Механически подгонять herdr под orca-шаблон при извлечении абстракции **нельзя**: обёртка
`\x1b[200~` уедет в промпт литералом.

Взаимоисключимость привязок при этом уже централизована (`applyBinding` в `editorStore`) —
с тремя таргетами шесть точек `delete` были бы миной.

### Фазы A и C — закрыты (web merge `942cb66`)

Три параллельных пути схлопнуты в провайдеров одного контракта (`lib/terminalTargets/`), три
пикера — в один с секциями herdr → Orca → tmux. Привязка стала одним полем `Tab.binding` с
дискриминантом `source`; легаси конвертируется в `normalizeTab` (нормализация на чтении, не
миграция — схема стора табов не менялась, bump БД не нужен). ~1450 строк на три пути → 850 на
общий механизм, бандл 416.8 → 402.9 kB.

**Что абстракция обнажила сама** (не искали специально — три дефекта, каждый из которых
жил незамеченным именно потому, что пути были параллельны):
- `Ctrl+T` показывал привязку **только для tmux** — Orca была невидима с момента внедрения,
  herdr с фазы B. Плюс фильтр «только привязанные» отбирал по любой привязке, но чип и тултип
  обещали tmux: интерфейс врал про собственное поведение (тот же класс, что «`Ctrl+P` = палитра»).
- Мёртвый tmux-путь: режим `"active"` (`display-message -p`) недостижим — единственный вызов
  уходил в clipboard по `!isTauri`.
- clipboard-фолбэк в трёх копиях, три расходящиеся формулировки тостов отправки.

**Граница абстракции — механика отправки НЕ унифицирована, и это решение, а не недоделка.**
tmux шлёт через `paste-buffer -p` + settle 80мс, Orca — ручной bracketed-paste + settle,
herdr — atomic `agent prompt` без обёртки и без settle. Подогнать herdr под общий шаблон
нельзя: `\x1b[200~` уедет в промпт литералом, а `--json` уронит команду. Предупреждение
продублировано в коде провайдера и в `web/CLAUDE.md` — это знание теряется между сессиями.

**Что зафиксировано в типах, а не в соглашениях:** `Resolution` разводит `not-found` и
`ambiguous` (раньше оба схлопывались в `null` — инвариант «не угадывать» соблюдался, но молча,
и пользователь не понимал, почему открылся пикер).

### Живой статус агента в StatusBar (после фаз A/C, web merge `cccada1`)

Абстракция окупилась третий раз: `statusOf(binding)` берёт статус из `listTargets()` провайдера
и находит свою строку через `sameBinding`. **Метода в контракте не добавилось** — статус уже
ехал в таргетах, его просто никто не читал. Orca получила индикатор бесплатно, tmux статусов
не отдаёт и чипа не показывает, ветки по источнику нигде нет.

**Подпись только у состояний, ждущих действия пользователя.** Это не вкусовое решение:
release-notes herdr 0.7.5 говорят «question prompts now report **blocked until the user answers**
or dismisses them», то есть `blocked` — единственное состояние, требующее реакции, остальные
информативны. Поэтому `blocked`/`waiting` получают подпись и пульсацию, прочее — тихая точка
с точным словом в тултипе. Побочно перестала гулять ширина полосы на каждом тике опроса.

**Опрос, а не подписка** — вынужденно: хуков от herdr к Sendoff не ведёт, а завести свои значило
бы поднять listener, что ломает no-egress-постуру редактора (см. заметку про agent-hooks выше).
**Цена замерена, а не прикинута:** ~1.8мс на вызов CLI (тонкий клиент к unix-сокету), ~0.2% ядра
при опросе раз в 3с. Кэш лейблов и растянутый интервал рассматривались и отброшены по замеру;
цифра записана в код, чтобы будущий агент не «оптимизировал» вслепую.

**неверна**. У herdr семантический слой есть, и он дешевле в потреблении. Вывод был

## Сессия 2026-08-07 — разбор жалоб 2-го пользователя (3 штуки)

Точка входа: «накопились баги + неудобства». Ни одна из трёх не оказалась тем, чем

### 1. Редактор гаснет после `Ctrl+A` + `Backspace` — **не наш баг, закрыт**

Симптом: на ~50 строках / ~5000 символов удаление всего текста оставляло пустое поле
без каретки и без плейсхолдера; помогал только перезапуск.

**Сценарий прогнан ровно в тех параметрах и в Chrome, и в WebKitGTK — оба чистые**
(`len=0`, фокус на месте, плейсхолдер отрисован, статус-бар `0 chars`). Диагноз дал сам
скриншот: статус-бар показывал `412 chars`, а плейсхолдера не было. Это взаимоисключимо
с «сломалось состояние» — раз плейсхолдера нет, в textarea лежит непустая строка; раз
статус-бар считает 412, она же в сторе. **DOM был прав, не отрисовались пиксели.**

Причина внешняя: `nvidia-utils 610.43.03-5 → 610.57.04-1` (2026-08-07, мажорный бамп);
`webkit2gtk` не менялся с 15 июля. После обновления баг ушёл на **том же бинаре** —
подтверждено автором. Тот же класс, под который в `lib.rs` уже стоит
`WEBKIT_DISABLE_DMABUF_RENDERER=1` (см. «Известные ограничения»).

**Кода не тронули намеренно.** Форсированная перерисовка чинила бы симптом чужого
дефекта и осталась бы обходом без жильца. Если класс вернётся, следующая ступень
лестницы — `WEBKIT_DISABLE_COMPOSITING_MODE=1` (по докам Tauri это «last resort»:
сносит аппаратный композитинг целиком). **Не начинать расследование заново с кода
редактора** — сначала сверить версии драйвера и webkit2gtk.

### 2. Фраза-триггер вставлялась в начало — **README врал, поведение стало настраиваемым**

Жалоба 2-го пользователя («так не должно быть») оказалась обоснованной с неожиданной
стороны: **оба README обещали «вставка по курсору» / «inserted at the cursor»**, а код
с самого начала клал префиксом в начало промпта. Тот же класс, что «`Ctrl+P` = палитра»
(2026-07-27): интерфейс описан не тем, что делает, и ожидание пользователя пришло из
документации.

Решение: настройка `phraseInsertMode` (`prepend` | `cursor`), дефолт — **исходное
поведение** (у автора мышечная память, у фраз роль префикса). README приведены к правде.
Аддитивный ключ в сторе `meta` → **bump версии БД не нужен**, данные не задеты.

Вставка читает текст и каретку **из самой textarea, а не из стора**: правки уезжают в
стор через RAF, и на быстром `Ctrl+K` сразу после набора стор отстаёт на кадр — вставка
по индексу из стора попала бы мимо.

### 3. «Herdr: Неизвестная ошибка» — **причина была на руках и выбрасывалась**

Невоспроизводимость была следствием, а не свойством бага. `useTerminalActions` описывал
ошибку как `error instanceof Error ? error.message : "Неизвестная ошибка"`, а
`tauri-plugin-shell` отклоняет промис **строкой** (ошибка из Rust, `Error` её никто не
оборачивает) — то есть единственная ветка, где текст ошибки существовал, вела в заглушку.

Введён `describeError` в `lib/terminalTargets/shell.ts` (рядом с бросающим `runScoped`) +
`console.error` с исходным значением. Первопричина сбоя у 2-го пользователя **остаётся
неизвестной** — в следующий раз она будет видна в тосте. Записано в гоча №9 `web/CLAUDE.md`.

называлась «Сохранить как .txt», модалка хоткеев — «Сохранить», оба README — «Save /
open file». **Пятый случай за две сессии, когда подпись врёт про поведение** (после
`Ctrl+P`, вставки фразы-триггера, «Herdr: Неизвестная ошибка»). Стоит считать это
системной проблемой, а не совпадением: подписи пишутся по намерению, а не по коду.

`isDirty` удалён из модели целиком, а не «снимается автоматически»: всегда-false флаг
оставил бы четыре ветки логики живыми на вид и мёртвыми на деле.

**Фактическая функция `Ctrl+S` была не «сохранить», а «разрешить закрывать этот таб
пачкой»**: `performCloseMany` фильтровал dirty-табы, поэтому при живом Ctrl+S «закрыть
остальные» почти всегда закрывало ноль. Это и раздражало.

Куда переехали гарды: подтверждение закрытия — на **наличие текста** (спрашивает реже:
пустые закрываются молча); bulk-close — на **подтверждение с числом** (без него «закрыть
остальные» при 75 табах унесло бы 74, из них 54 безвозвратно — стек возврата 20 и только
в памяти); предупреждение при закрытии окна — на `flushSession()`; «Закрыть все
сохранённые» удалена (смысл исчез, «Закрыть пустые» уже есть).

### Тесты — взяты, но по цене ошибки, а не по объёму кода

Решение принято не «пора бы»: **жильцы уже существовали**. Каждую сессию писались
проверочные скрипты в scratchpad (14/14 конверсии легаси, 7/7 herdr-резолва, 27/27
markdown, 11 форм ошибок) — и каждый раз выбрасывались.

`bun test` (встроен, отдельного раннера нет), одна dev-зависимость `fake-indexeddb`.
69 тестов: резолв tmux/herdr, `normalizeTab`, слой БД с апгрейдами v5→v6 и v1→v6,
`sameBinding`/`describeError`/сужение вывода CLI.

**Компоненты и хуки не покрыты сознательно** — ломаются от вёрстки, а не от багов.
CI тоже не заводили: сначала пусть тесты поживут.

⚠️ **Тесты сразу нашли настоящий баг:** `getDB()` открывал новое соединение с IndexedDB
на каждый вызов и не закрывал. Проблема не в утечке — открытые соединения **блокируют
апгрейд версии**, то есть следующий же bump `DB_VERSION` повис бы у обоих пользователей
навсегда. Соединение теперь кэшируется. Ровно тот класс, ради которого тесты и брали.

### Закрытие таба — модель Obsidian (та же сессия)

Автор уточнил, что хотел «как в Obsidian». Сверка показала: **по сохранению мы Obsidian
уже повторили** — он пишет по таймеру ~2 с, флага «не сохранено» не показывает, `Ctrl+S`
лишь форсирует запись. У нас всё то же, и пишем чаще (0.5 с).

Непохожим оставалось **закрытие**. В Obsidian вкладка — окно в документ: закрыл, а заметка
осталась файлом в хранилище. У нас таб И ЕСТЬ документ, поэтому закрытие удаляло, а стек
возврата жил в памяти и хранил 20. Именно поэтому и понадобилось подтверждение.

Архив закрытых теперь персистится (потолок 20 → 200), подтверждение при закрытии одного
таба убрано. У пакетного оставлено, но с другим основанием: не потеря данных, а масштаб.

**Bump версии БД не понадобился:** архив лежит в сторе `tabs` с маркером `closedAt`, а
форма записи внутри таба версию менять не обязана. Новый object store потребовал бы v7 и
сломал бы 2-му пользователю откат на старый бинарь. Расщепление живые/архив — на границе
персистенса, поэтому архив не может протечь в полосу или поиск.

## Сессия 2026-08-09 (часть 2) — `linuxdeploy` починен, блокер стадии B снят

Единственный блокер prebuilt-релиза, висевший с 2026-07-07, закрыт однострочной правкой.

**Диагноз.** `bun run build` падал на `failed to bundle project 'failed to run linuxdeploy'` —
сообщение без причины, ровно того же класса, что «Herdr: Неизвестная ошибка». `deb` и `rpm`
при этом собирались нормально, то есть ломалась только AppImage-стадия. Запуск `linuxdeploy`
руками показал настоящую ошибку:

```
strip: libzstd.so.1: unknown type [0x13] section `.relr.dyn'
strip: Unable to recognise the format of the input file
```

`linuxdeploy` — сам AppImage и таскает внутри **свой** `strip` из старых binutils. Библиотеки
Arch собраны с `-z pack-relative-relocs` и содержат секцию `.relr.dyn` (`SHT_RELR`, тип
`0x13`), которой тот `strip` не знает. Падает **не сборка, а стрип чужих библиотек**.

**Гипотезы, которые оказались неверны** (проверены до того, как лезть в код): FUSE2
отсутствует — нет, `libfuse.so.2` на месте; unprivileged user namespaces запрещены — нет,
`kernel.unprivileged_userns_clone = 1`. Симптом выглядел как классический «AppImage не
монтируется», но им не был.

**Фикс:** `NO_STRIP=1` в скрипте `build` в `package.json` (штатный выключатель linuxdeploy).

**Цена измерена, а не оценена на глаз:** AppDir 287 → 283 МБ, то есть системный `strip`
экономит 1.4%. Библиотеки Arch и так поставляются стрипнутыми (отладочные символы — в
отдельных пакетах `*-debug`). Поэтому усложнять (пре-стрип AppDir системным binutils,
свой вызов linuxdeploy в обход Tauri) смысла нет.

**Проверено артефактом, а не только кодом возврата:** `bun run build` = 0, три бандла —
`Rewrite_0.1.0_amd64.AppImage` 97.2 МБ, `.deb` 5.6 МБ, `.rpm` 5.6 МБ. AppImage запущен
на изолированных `XDG_DATA_HOME` / `XDG_CONFIG_HOME` (чтобы вторая копия не легла в рабочую
IndexedDB автора), поднялся, создал собственный `dev.sendoff.app/databases`, прожил 14 с,
RSS 17 МБ, остановлен. Рабочий инстанс автора не тронут.

**Что этим НЕ сделано** (на момент части 2): сам GitHub Release не выпущен, CI нет,
Windows/macOS не трогали. Снят блокер, а не закрыта стадия B целиком. → Релиз выпущен в
части 3, см. ниже.

## Сессия 2026-08-09 (часть 3) — артефакт, который действительно запускается

Починенный `linuxdeploy` дал собираемый AppImage, но **не пригодный к публикации**, и это
выяснилось до выпуска, а не после.

**Находка.** AppImage бандлит библиотеки, но **не glibc**. Внутрь кладутся системные
библиотеки сборочной машины, а они требуют её glibc. Замер собранного на Arch артефакта:
бинарь — `GLIBC_2.39`, забандленные библиотеки (`libwebkit2gtk`, `libglib`,
`libjavascriptcoregtk` и ещё 170) — **`GLIBC_2.43`**. Для сравнения: Ubuntu 24.04 LTS — 2.39,
Debian 13 — 2.41. То есть артефакт работал бы почти только на Arch — ровно у тех, кто и так
собирает из исходников. Выложить его как «prebuilt Linux artifact» значило бы дать обещание,
которое не выполняется у большинства.

**Решение — контейнерная сборка** (`Dockerfile`, Ubuntu 22.04, glibc 2.35). Штатная практика:
собирать на самом старом дистрибутиве, который поддерживаешь. Результат: библиотеки требуют
максимум **2.35** → Ubuntu 22.04+, Debian 12+, Fedora 36+, Arch. Размер заодно 97 → 83 МБ.

Две ловушки, обе штатно обходятся и обе записаны в `Dockerfile`:
1. **В Docker без `--privileged` нет FUSE**, а `linuxdeploy` — сам AppImage и не смонтируется.
   Лечится `APPIMAGE_EXTRACT_AND_RUN=1`.
2. **Отдельный `CARGO_TARGET_DIR`** обязателен: иначе Arch- и Ubuntu-объектники перетирают
   друг друга и каждая следующая сборка идёт с нуля.

**Проверка сделана так, чтобы отличить «собралось» от «работает».** Артефакт запущен в
**чистой** `ubuntu:22.04` без единого dev-пакета и без webkit в системе. Он дошёл до
`Failed to initialize GTK` — то есть упёрся в отсутствие дисплея, а **не** в символы glibc и
не в отсутствующий webkit. Это и есть доказательство: все 167 библиотек загрузились, webkit
приехал из самого AppImage. Отдельно тот же файл запущен на Arch с реальным дисплеем
(изолированные `XDG_*`, своя IndexedDB) — окно поднялось.

**Побочно выяснен полный список того, что AppImage ждёт от хоста** (excludelist самого
linuxdeploy, бандлить это вредно): `libEGL`, `libGL`, `libX11`, `libX11-xcb`, `libxcb`,
`libdrm`, `libgbm`, `libexpat`, `libfontconfig`, `libfreetype`, `libharfbuzz`, `libfribidi`.
На любом десктопе они есть; в голом контейнере — нет. Записано в README, чтобы «не
запускается» не превратилось в нерасследуемый баг-репорт.

**`.deb` и `.rpm` собираются, но НЕ публикуются.** Они выходят из той же команды, но их никто
не ставил на Debian или Fedora, а проверить автор не может. Непроверенный пакет в публичном
релизе хуже его отсутствия: он выглядит обещанием поддержки, которого нет.

**Заодно исправлено враньё в README:** все четыре файла утверждали «no tests / без тестов» —
неверно с 2026-08-08, когда завели `bun test` (93 теста). Плюс снята оговорка про падающий
`linuxdeploy` и «готовых релизов пока нет».

1. **`wf-recorder` врёт про диапазон яркости.** Данные кладёт в 16..235 («телевизионный»

## Сессия 2026-08-11 (часть 2) — релиз `v0.1.1`: гард доехал до артефакта

### Почему пересобрали, хотя фич не добавилось

`v0.1.0` опубликован 2026-08-09, а гард single-instance сделан 2026-08-10 — то есть
**опубликованный артефакт нёс баг с потерей данных**, уже закрытый в исходниках. Формулировка
риска «скачавший получит пустой экран» его занижала: пустой экран получает только тот, кто
раньше собирал из исходников, а **потерю табов от второго запуска — любой, включая нового
пользователя**. Стадия C и Download на лендинге ведут ровно на этот ассет, поэтому пересборка —
предусловие продвижения, а не косметика.

### Почему новый тег, а не подмена ассета

Подменить файл под `v0.1.0` технически можно, но в notes того релиза записан sha256, сверенный
побайтово после публикации. Замена сделала бы записанную проверку ложной, а скачавшие раньше не
узнали бы, что файл под тем же именем стал другим. `v0.1.0` оставлен как есть.

### Находка: «фокусирует существующее окно» — обещание, которого нет

README (обе версии) утверждали, что повторный запуск **фокусирует** уже открытое окно. Замерено —
**не фокусирует**: после второго запуска активным остаётся то окно, что было активно до него.
Причина не в нашем коде: Wayland-композиторы игнорируют запрос активации от процесса, с которым
пользователь только что не взаимодействовал, а токена активации у второго инстанса нет.

**Проверено на обеих сборках** — AppImage и установленная из исходников дают одинаковый результат,
то есть это не свойство XWayland-пути AppImage. Гард при этом работает: второе окно не
открывается, первый инстанс жив.

Седьмой случай в проекте, когда подпись обещает больше, чем делает код. README приведены к правде;
чинить активацию не стали — ценность гарда в том, что он не даёт затереть базу, а не в фокусе.
Если возвращаться — смотреть в сторону `xdg-activation` / `request_user_attention` (у niri есть
`is_urgent`), это отдельная работа с пересборкой.

### Грабли стенда, не приложения (чтобы не потерять день заново)

1. **`app_id` у двух сборок разный:** AppImage выставляет `Sendoff-desktop` (с заглавной),
   сборка из исходников — `sendoff-desktop`. Счётчик окон по точному совпадению даёт ноль при
   живом окне. Важно и практически: правила окон в композиторе, написанные под одну сборку, не
   сработают для другой.
2. **`kill` по pid обёртки AppImage не убивает приложение** — внутренний `sendoff-desktop`
   переживает и продолжает держать окно и имя на шине. Следующий запуск после этого выходит
   по гарду, и это легко принять за сбой старта.
3. **Фиксированная пауза «подождать окно» не годится:** под `dbus-run-session` порталы
   поднимаются с нуля. Ждать надо появления окна по факту, иначе быстрый выход второго инстанса
   неотличим от «первый не стартовал».

## Сессия 2026-08-12 — слэш-меню (`/`), спек `tasks/17`

### Основание — не «в Obsidian так»

Идея пришла со скриншотов Obsidian, но перенос «как есть» отвергнут: Obsidian — редактор
заметок, markdown там конечный продукт; в Sendoff markdown — леса вокруг промпта, который
уезжает в терминал агента.

Настоящее основание нашлось при разборе второй половины запроса — про клавиатуру. **`/` —
единственный триггер вообще без модификаторов.** Все 36 команд реестра сидят на `Ctrl`+что-то,
часть с `Shift`/`Alt`. Основная клавиатура автора — 60% (Cidoo QK61 v2): нет F-ряда, стрелок и
nav-кластера. Меню на одной клавише — не «ещё один хоткей», а снятие хоткеев.

### GitHub Alerts выкинуты (5 из 13 пунктов исходной идеи)

`> [!WARNING]`, `> [!NOTE]` и остальные — синтаксис рендеринга GitHub. В промпте Claude Code он
не рендерится ничем, а «важно» дешевле сказать словом. Автор подтвердил: в Sendoff пишутся
только промпты, доки — нет. **Условие пересмотра:** если README/issues начнут набираться здесь.

### Фразы-триггеры внутри меню, всегда в каретку

Решено пустить `triggerPhrases` в тот же список: для prompt-first именно они ценный груз, а
markdown — генерика. Расхождение с `Ctrl+K` в режиме `phraseInsertMode: "prepend"` (дефолт —
префиксом ко всему промпту) принято **сознательно**: `/` вызывается в конкретной точке текста,
вставка в начало таба противоречила бы жесту. Настройка и поведение `Ctrl+K` не тронуты.

### Что вскрылось попутно: переставить таб фактически нечем

Разбор реестра под 60% клавиатуру дал находку, которую по отдельности не замечали два месяца.
Переставить таб можно двумя способами, и оба нерабочие:

1. `Ctrl+Shift+PgUp` / `Ctrl+Shift+PgDn` — **единственная** привязка move-tab, а `PgUp`/`PgDn` на
   60% живут на Fn-слое. Итого четыре пальца. У соседних `next-tab`/`previous-tab` альтернатива
   есть (`Ctrl+Tab`), у move-tab — нет.
2. DnD ровно **на одну позицию вправо** — no-op (`reorderTab` вставляет на индекс цели), дефект
   известен с 2026-08-07.

Чинится дёшево (второй аккорд без nav-клавиш + правка `reorderTab`), сначала **вынесено
отдельной задачей** по решению автора, затем в том же дне сделано — см. ниже.

### Перестановка таба починена (web merge `47ff000`)

**DnD.** Вставка шла всегда «перед целью». На шаге вправо это математически no-op: таб
вынимается, цель съезжает на освободившееся место, вставка перед целью возвращает таб ровно
туда, откуда взяли. Влево тот же код работал верно — потому дефект и выглядел мистикой.
Теперь при движении вправо таб встаёт **после** цели.

Арифметика вынесена в чистую `reorderTabs` в `lib/tabUtils.ts` (стор только зовёт) — иначе её
нечем было бы покрыть тестом, а именно арифметика и врала. Побочно вскрылось второе: членство
в группе бралось у соседа по **индексу вставки**, а при движении вправо там стоит уже следующий
таб — с чужой группой. Теперь берётся у цели броска.

**Аккорд.** Добавлены `Ctrl+Shift+,` / `Ctrl+Shift+.` вторыми аккордами (мнемоника «<» / «>»,
буквенный ряд есть на любой клавиатуре). `Ctrl+,` и `Ctrl+.` не задеты: `matchesChord` требует
точного равенства всех модификаторов, проверено живьём.

**Два инварианта реестра закрыты тестами**, потому что оба класса ошибок тихие:
- ни один аккорд не занят двумя командами одной области — `matchShortcut` отдаёт первую
  подошедшую и вторую делает молча недостижимой, без единой ошибки в консоли;
- у команд на nav-клавишах есть аккорд без них — иначе команда снова окажется недоступной на
  60% клавиатуре, и заметит это только тот, у кого такая клавиатура.

### Грабли, записанные в `web/CLAUDE.md`

- Детект триггера идёт **по тексту слева от каретки, не по коду клавиши**: на ЙЦУКЕН физическая
  `Slash` даёт «.», проверка по `e.code`/`e.key` открывала бы меню не от того символа.
- `Escape` обязан помечать **конкретный слэш** закрытым. Без этого следующая же буква открывает
  меню снова, и написать «/h2» текстом невозможно в принципе.
- Секции ранжируются **внутри себя**, порядок секций фиксирован: сквозная сортировка по очкам
  перемешала бы фразы с markdown и нарисовала заголовок секции по нескольку раз.

## Сессия 2026-08-13 — переименование Rewrite → **Sendoff**

Точка входа: лендинг под стадию C. Отложен на один заход — имя несёт домен, обложку и
заголовок поста, и переделывать его через неделю дороже, чем решить сейчас.

### Почему имя менялось

Не из-за коллизии как таковой. Коллизии есть — [`openrewrite/rewrite`](https://github.com/openrewrite/rewrite)
(★13k+, Apache-2, движок массового рефакторинга за компанией Moderne) и «Rewrite» как имя
AI-перефраза **во всём Microsoft 365** (Word, Outlook, Teams, PowerPoint, OneNote, SharePoint;
Word прямо зовёт это «AI rewriter and paraphraser»). Но сами по себе они терпимы: OpenRewrite
живёт в JVM-мире, пересечение аудиторий мало.

Решающим было другое: **имя обещало ровно ту вещь, от которой продукт сознательно отказался.**
`rewrite-cli` как LLM-переписывалка отклонён 2026-06-16 (сеть и API-ключи ломают границу
no-egress), а вывеска продолжала читаться как «AI-перефразер». Этот налог платился бы в каждом
треде на HN и реддите. Восьмой случай в проекте, когда подпись обещает не то, что делает код —
только на этот раз подпись была на вывеске.

Момент выбран не случайно: после Show HN имя уезжает в перманентные ссылки и заголовки тредов.
Это тот случай, где YAGNI отступает по пункту **reversibility**.

### Как выбиралось (критерий — не вкус, а занятость namespace)

Гейтом была коллизия в dev-экосистеме (GitHub / crates.io), а **не** свободный `*.pages.dev`:
поддомены на обычные слова разобраны сквоттерами, и давать им право вето на имя продукта —
хвост виляет собакой.

Выбито по числам, а не по ощущению: `nock` (★13k, HTTP-моки для Node — а `web/` это JS/TS),
`salvo` (★4.4k, веб-фреймворк **на Rust**), `quiver` (★3.6k, и это **веб-редактор**),
`sluice` (настоящий крейт, 16 млн загрузок), `slipway` (числа GitHub-поиска соврали: под этим
именем целая организация плюс деплой-платформа, контейнерный тул и «session desk for
shipping work» — слово оказалось популярным выбором именно для dev-тулинга).

**Приставка `open-` рассмотрена и отклонена.** Она не даёт уникальности, а притягивает
коллизию: `opencode` — это **два разных** проекта с одним именем (★196k и ★13.6k, оба
терминальные кодинг-агенты), `openusage` — три, репозиториев с `open` в имени — 1 037 069.
Плюс семантика: `open-` значит «открытый аналог известного закрытого», а Sendoff ничего не
переоткрывает. И отдельная ирония: `openrewrite` — буквально `open` + прежнее имя.

**Sendoff** выбран из трёх финалистов (Sendoff / Souffleur / Onager) за то, что наполовину
объясняет себя через `send`, не скатываясь в `prompt*`-пыль (141 827 репозиториев со словом
`prompt` в имени — это не «понятно», это невидимо).

### Что переехало и что намеренно НЕ переехало

| | |
|---|---|
| Репозитории | `exviolet/sendoff` (продукт, релизы) · `exviolet/sendoff-web` (фронтенд-сабмодуль) |
| `identifier` | `com.rewrite.app` → `dev.sendoff.app` + перенос каталога данных в `update.sh` |
| Бинарь / иконка / `.desktop` | `sendoff-desktop` / `sendoff.png` / `dev.sendoff.app.desktop` |
| Версия | 0.1.1 → **0.2.0** (меняется путь к данным и имя бинаря — patch такого не обещает) |
| **`DB_NAME`** | **остаётся `rewrite-db`** |

**Репозитории поменялись местами намеренно.** Раньше каноничное короткое имя носила
браузерная сборка, которая не умеет главного (отправки в терминал), а продукт прятался за
суффиксом `-desktop`. Человек с HN шёл по короткой ссылке в урезанный вариант.

**`DB_NAME` не переименован и не будет.** Имя базы — это путь к данным, а не подпись: другое
имя открыло бы пустую базу, а накопленное осталось бы лежать рядом невидимым. Снаружи оно не
показывается никому. В `db.ts` рядом положен комментарий, чтобы следующий заход его не
«причесал». Тот же принцип развёл переименование бренда и `identifier` как два независимых
решения — второе тронуто только потому, что каталог виден всем будущим пользователям.

**Глагол `rewrite` не тронут** нигде: комментарии «Clear and rewrite tabs», id пресетов
`rewrite-formal`/`rewrite-friendly` (они значат «переписать тон»), «a save rewrites the whole
snapshot». Факты о выпущенных артефактах (`Rewrite_0.1.0_amd64.AppImage` и записанный рядом
sha256) тоже оставлены — файл на GitHub действительно так называется.

### Перенос данных: почему не просто `mv`

`update.sh` переносит `~/.local/share/com.rewrite.app` → `dev.sendoff.app` **первым шагом, до
сборки**, и отказывается работать, если существуют **оба** каталога: два каталога означают, что
новый бинарь уже запускали и он завёл пустую базу, а слепой `mv` в этот момент уничтожил бы
накопленное. Проверено на четырёх сценариях (только старый / оба / только новый / повторный
запуск) на копиях, не на живых данных.

### Найдено попутно

**`StartupWMClass` не совпадал с реальностью с самого начала.** В `.desktop` стояло
`StartupWMClass=Rewrite`, а фактический `app_id` окна — `rewrite-desktop` (замерено на живом
окне через `niri msg -j windows`). То есть окно не связывалось с пунктом меню. Теперь стоит
настоящее значение `sendoff-desktop`.

**Демо частично протухло от переименования.** Имя продукта в кадре не появляется, но в правой
части видно `~/Projects/Personal/Desktop/rewrite-desktop` и `[ex1te@exite rewrite-desktop]` в
статус-строке. Пересъёмка ручная (набор автоматизировать нельзя, см. сессию 2026-08-11) —
предусловие постинга, не блокер сборки.

### Прецедент

Проект переименовывался и раньше: `RewriteBox → Rewrite` (2026-04-15). Тогда вместе с
`identifier` осиротел каталог `~/.local/share/com.rewritebox.app` — он до сих пор лежит на
диске (12 МБ, последняя запись 2026-03-29). Ровно поэтому в этот раз перенос данных написан
явно, а не оставлен пользователю.

## Сессия 2026-08-13 (часть 2) — правка workspace доехала до пикера

### Основание — не «не хватает CRUD», а функция без обнаружимости

`renameWorkspace` и `deleteWorkspace` жили в сторе и в палитре с самого v1 (2026-07-10). Но
обе команды открывали `ConfirmDialog` **над активным** workspace: диалог брал
`activeWorkspaceId` в момент рендера, поэтому переименовать выбранную в пикере строку было
нечем — только ту, в которой уже сидишь. В самом пикере не было ни кнопки, ни подсказки.

Это тот же класс, что `Ctrl+Shift+A`, не задокументированный **вообще** (сессия 2026-08-08):
код умеет, пользователь не знает. Разница в том, что здесь путь был не просто скрыт, а
**вёл не туда** — переименовать чужую строку было нельзя в принципе.

### Почему второй вид модалки, а не диалог поверх пикера

Диалог поверх пробовали первым, он сломался предсказуемо: `PickerModal` и `ConfirmDialog`
оба слушают `keydown` в **capture-фазе**, пикер зарегистрирован раньше и забирает
`Enter`/`Esc` себе. Чтобы диалог получил свои клавиши, примитиву нужен `disabled` — и после
этого всё равно остаются два наложенных слоя друг над другом.

Второй вид той же модалки (`list` / `edit`, по образцу `TriggerPhrasePicker`) дешевле и
честнее. Что при этом **обязательно** — четыре пункта, каждый ловится только руками:

- `disabled: view !== "list"` — в правке стрелки и `Enter` должны быть нативными (это ввод
  в поле имени), а `Esc` обязан вернуть в список, а не закрыть модалку.
- **Фокус в поиск при возврате** — примитив фокусирует `inputRef` только на маунте.
- **Кламп `selectedIndex` после удаления** — примитив клампит только на `ArrowDown`, иначе
  курсор виснет за концом укоротившегося списка.
- **Последствие удаления — текстом рядом с кнопкой**, а не в диалоге после клика.

### Удаление: последствие несимметрично, поэтому написано до клика

Удаление workspace **уносит табы** в первый оставшийся, но **стирает группы** — вернуть их
нечем. Поэтому цена написана рядом с кнопкой (читается ДО клика), а сам `Delete` взводится
вторым кликом (`Delete` → `Confirm delete`). Отдельного диалога подтверждения нет.

Обе команды палитры (`rename` и `delete`) теперь ведут в одну и ту же панель правки. Две
записи оставлены намеренно — ради поиска по слову «delete».

### Побочно: строка пикера с действием

Строка с кнопками стала `<div>`, а не `<button>` — кнопки не вкладываются друг в друга.
`data-picker-index` переехал на контейнер (доскроллу примитива важен атрибут, не тег).
Счётчик держится крайним правым столбцом фиксированной ширины, а место под появляющуюся
надпись `edit` занято всегда (`invisible`), иначе колонка ездит от выделения строки.

Правила записаны в `web/CLAUDE.md` — они относятся ко всем пикерам, не только к этому.

**Гейт:** `tsc -b` 0, `lint` 0, 134/134. Новых тестов нет: изменение чисто компонентное, а
компоненты тестами не покрыты — тестами закрыта чистая логика и слой IndexedDB.

## Сессия 2026-08-14 — `image → path`: idea #1 закрыта

Открытая ветвь с 2026-06-30. Предусловием значился «грилл канала картинка → агент» — он и
оказался главным, потому что снял с задачи половину заявленной цены.

### Спайк: канал работает, и одинаково у обоих агентов

Тест построен так, чтобы галлюцинация не прошла за успех: картинка со **случайным
шестизначным числом** и фигурой, содержимое из имени файла не выводится.

| Агент | Что сделал | Ответ |
|---|---|---|
| Codex `gpt-5.6-sol medium` | шаг «Viewed Image» | красный треугольник, **934785** |
| Claude Code `Haiku 4.5` | `Read image (3.2KB)` | треугольник, красный, **934785** |

Оба назвали число — значит файл читали. Расхождения между агентами нет, фича не зависит от
того, к чему привязан таб.

**Второй прогон («голый путь без просьбы») отменён как бессмысленный.** В реальном потоке
путь вставляется ВНУТРЬ промпта, который пользователь и так пишет, — просьба там уже есть.
Голый путь из редактора промптов никто не отправляет. Побочно выяснилось, что Claude Code
принимает картинку и прямо в свой инпут, но это конкурирующий путь ценой в ноль кода: он
требует уйти в терминал, ради чего Sendoff и существует.

### Главное: заявленная цена оказалась ценой одного канала из трёх

Роадмап обещал «требует fs-write permission + расширение threat model». По факту:

| Канал | Что нужно | Новая permission |
|---|---|---|
| drag & drop файла | вставить `event.payload.paths` вместо игнора | **нет** — путь уже приходил в `onDragDropEvent`, его молча выбрасывал фильтр по расширению |
| выбор через диалог | `dialog.open()` → путь | **нет** — `dialog:default` выдан давно |
| `Ctrl+V` из буфера | материализовать байты | да |

Автор выбрал второй и третий; drag & drop отложили как «бесплатный, но без жильца» — и
**закрыли следующей же сессией**, см. ниже.

### Почему НЕ `fs:allow-write-file`

Проверено в `gen/schemas/acl-manifests.json` установленной версии (`tauri 2.10.3`,
`tauri-plugin-fs 2.4.5`): эта permission открывает **три** команды — `write_file`, `open`,
`write`, — при том что её собственное `description` упоминает только первую. `open` в этом
плагине не декоративен: он существует отдельной permission `allow-open` и входит в наборы
`read-files`/`read-all`.

Сегодняшний baseline для сравнения: `fs:default` (набор `create-app-specific-dirs` +
`read-app-specific-dirs-recursive` + `deny-default`) плюс `allow-read-text-file` и
`allow-write-text-file`. То есть у вебвью **нет ни одной команды записи, кроме текстовой, и
нет `open`**. Выдать generic open+write по всему `fs:scope-home-recursive` ради одного PNG —
несоразмерно.

**Взято:** своя команда `save_clipboard_image`. Вебвью передаёт только байты; каталог из
`app_local_data_dir()`, имя генерируется, расширение выводится из **сигнатуры файла** — путь
вида `../../evil.sh` невозможен не по проверке, а по отсутствию входа.

**И заведена в ACL через `AppManifest::commands`.** Команды приложения по умолчанию разрешены
всем окнам и в `capabilities` не попадают — запись файлов стала бы невидимой в манифесте, а
именно там у проекта описана граница. Теперь выдаётся явно, одной строкой, как плагинная.

### Платформенная находка, стоившая прогона вслепую

Первая версия не работала совсем, и причина не наша: **WebKitGTK не отдаёт вставленную
картинку в событии `paste` никак** — ни `clipboardData.files`, ни `clipboardData.items`.
Замерено на живом приложении при скриншоте в буфере (`wl-paste --list-types` показывал ровно
`image/png`): проверялись все три пути сразу, сработал только асинхронный
`navigator.clipboard.read()`, и звать его надо внутри обработчика вставки — это жест
пользователя. Привычный по Chrome/Firefox код «взять файл из DataTransfer» здесь молча не
делает ничего.

Диагностика построена так, что **один прогон пользователя дал и починку, и замер**: три пути
пробовались подряд, тост называл сработавший. Синтетический `Ctrl+V` был бы дешевле, но
`wtype` не проводит модификаторные сочетания — это уже знали с сессии про демо.

Записано отдельной gotcha в `web/CLAUDE.md`: класс ошибок тихий.

### Прочее

MIME-тип с фронта не проверяется вообще: WebKitGTK кладёт файл с пустым `type`. Строгости это
не стоит — формат решает сигнатура в Rust. Вставляется голый путь, без `![](…)`: терминальный
агент markdown не рендерит (то же основание, по которому выброшены GitHub Alerts).

Очистка накопленных картинок **не делается** — решение автора: удалить картинку, которая ещё
нужна агенту, хуже, чем хранить сотню скриншотов. Вернуться, когда каталог станет заметен.

## Сессия 2026-08-14 (часть 2) — drag & drop закрыт, и вскрыл чужой баг

Канал стоил ровно того, во что его оценили: путь уже приходил в `onDragDropEvent`, новых
permissions не понадобилось. Два обязательства, каждое ловится только руками — все картинки
одной вставкой (каретка после `updateContent` доезжает лишь следующим кадром, цикл положил бы
второй путь до первого) и картинки **до** текстовых файлов (`addTabFromFile` заводит новый таб
и делает его активным).

### Чистка каталога: решено не строить, и основание не «потом»

Замер вместо оценки: после целой сессии постройки и живых прогонов в каталоге лежал **один
файл, 620 КБ**. Три вещи, которые меняют картину сильнее размера:

- **Пишет файлы только канал «буфер».** Диалог и drag & drop ничего не копируют — они
  ссылаются на файл, который уже лежит у пользователя. То есть новый канал **снижает** приток:
  сохранённый скриншот теперь бросается, а не пересохраняется второй копией.
- **Чистка по возрасту тихо ломающая.** Путь живёт внутри текста таба, а табы персистятся
  вечно (75+ живых, архив закрытых до 200). «Удалить всё старше N дней» превращает старые
  промпты в битые ссылки, и узнаётся это через месяц после срабатывания. Тот же класс, что
  дефект переноса каталога перед `v0.2.0`: ломается молча, потому что читать нечего.
- **Безопасная форма существует, но не дешёвая.** Честная чистка — по достижимости: удалять
  только файлы, на которые не ссылается ни один таб, включая архивные. Это скан по содержимому
  всех табов плюс **ещё одна Rust-команда на удаление** — ровно тот размен, от которого
  отказались в случае `fs:allow-write-file`.

Цена бездействия: ~600 КБ на вставку, сотня вставок ≈ 60 МБ. Возврат — когда каталог станет
заметен, и тогда **по достижимости, не по возрасту**.

### Побочно: пре-существующий баг, который фича сделала видимым

Слушатель `onDragDropEvent` регистрируется за двумя `await` (динамические импорты), а cleanup
эффекта возвращается немедленно. Свернули эффект в этом промежутке — cleanup видит `unlisten`
пустым, отписаться не может, слушатель живёт до конца сессии. В `StrictMode` это не гонка, а
гарантия: React монтирует эффекты дважды.

**Баг существовал с самого начала и бил по текстовым файлам:** брошенный один `.md` открывал
**два** таба. Не замечали, пока тот же код не начал вставлять путь картинки — два одинаковых
таба списываются на промах мышью, два одинаковых пути в строке не спутать ни с чем. Девятый
случай в проекте, когда старый дефект вскрыла новая фича, прошедшая по тому же коду, а не тест.

В release-сборке `StrictMode` эффекты не задваивает, поэтому в `v0.2.0` этого нет и чинить
задним числом нечего. Готча №11 в `web/CLAUDE.md`.

## Сессия 2026-08-18 — Sendoff Doctor + first-send онбординг

Первое, что видит скачавший Sendoff, — пустой редактор с «Untitled» и «Start typing or
paste text». Ни намёка на то, ради чего продукт существует.

### Онбординг сужен до одного сценария (Issue #5 переписана)

Исходный wizard (тема → шрифт → workspace → рассказ про send) **отклонён**: это settings
maze, и предупреждение об этом лежало в самой issue с 2026-07-10. Осталась ровно одна
проверяемая цепочка: **открыл → увидел таргет → привязал → написал → `Ctrl+Enter` →
увидел подтверждение**. Ни темы, ни шрифта, ни workspace, ни хоткеев, ни групп.

- **Не запирает редактор.** `Continue without a target` и Escape доступны всегда: без
  таргета Sendoff остаётся рабочим редактором, и обязательный wizard врал бы про это.
- **Пустое состояние не тупик:** `Try again` + `Open Sendoff Doctor`.
- **Завершение — по факту успешной отправки** (`sendVia`), а не по привязке.

### Граница честности: «отправлено», а не «получено»

Sendoff вправе утверждать только, что его собственный send-path отработал. Читал ли агент
промпт — неизвестно: `capture-pane` отклонён 2026-06-16 после спайка. Поэтому финальное
подтверждение — существующий тост `Sent to Herdr: … (N chars)`, и формулировки уровня
«agent received your message» в продукте не появляются.

### Пустая база ≠ первый запуск

Ключевая ловушка гейта. `storageError` приходит только когда чтение **упало**, а
задокументированный дефект переноса каталога (`Rewrite → Sendoff`, `src-tauri/src/lib.rs`)
даёт другое: чтение проходит, читать нечего, баннера нет. Плюс у 2-го пользователя ключа
нет вовсе — фича новее его базы.

Гейт: `storageError` → не показывать никогда; ключ есть → не показывать; ключа нет и есть
реальные данные → **тихий backfill**; ключа нет и база нетронута → показать.

- **`onboardingVersion` — число, не флаг**, в существующем сторе `meta`. Bump `DB_VERSION`
  не нужен (он ломает откат 2-го пользователя), стор `meta` в `saveSession` не чистится.
  Запись отдельная, не через снапшот: тот дебаунсится 500 мс, и убитый процесс вернул бы
  онбординг уже прошедшему.
- **«Любой ключ в meta» как признак — отклонено.** Слишком широкий контракт: первый же
  служебный ключ будущей фичи молча подавил бы онбординг у нового пользователя. Признаки
  перечислены явно и закрытым списком (`hasExistingUserData`), причём **content-based**:
  `hydrate` сам создаёт «Untitled 1» и workspace «Default», а пресеты и trigger phrases
  сидируются дефолтами — ни то, ни другое признаком не является.

### Sendoff Doctor (Issue #10) — только показывает

Ничего не чинит и не настраивает. Два уже случившихся инцидента были нерасследуемы:
отказ **валидатора send-пути** (herdr `pane_id` против регекса в манифесте) и отказ чтения
IndexedDB из-за **разницы версий WebKit**.

- **`not-installed` отклонён как формулировка.** Sendoff знает только, виден ли бинарь в
  **его собственном** PATH: у GUI-запуска PATH урезанный (ровно поэтому `lib.rs` дотягивает
  `~/.local/bin`). Текст — `Executable not found in Sendoff PATH`.
- **Хендл каждого таргета — в отчёте.** Инцидент с herdr имел полностью зелёный discovery
  при сломанной отправке: discovery-команды herdr валидаторов не имеют вовсе. Видимый
  формат хендла ловит этот класс без пробной отправки (она была бы спамом в живого агента).

### Архитектура диагностики: два сигнала вместо парсинга строк

`tauri-plugin-shell` схлопывает **все** варианты `scope::Error` в одно `ProgramNotAllowed`
(`commands.rs`, настоящая причина — только под `#[cfg(debug_assertions)]`). Различать
исходы по тексту = регексить чужие сообщения.

Взят второй, независимый сигнал: наличие файла в PATH (Rust-команда, обход PATH **без
запуска процесса**). Статус выводится из пары: `discovery ok → ready`;
`упал + файла нет → not-found`; `упал + файл есть → error` + сырое сообщение.

- **`isAvailable()` не возвращён** — он отклонён отдельно в `types.ts`, и пикер продолжает
  работать по отклонённому промису, продуктовый путь не тронут.
- **`diagnose()` в `TerminalProvider` не добавлен.** Все три провайдера падают одинаково,
  через общий `runScoped` → классификация одна на всех, снаружи. Метод появится, когда
  появится провайдер с другой моделью отказов.
- **Расширение контракта — одно поле `executable`.** Из JS имя бинаря иначе не узнать:
  в манифесте `name` entry и `cmd` — разные строки, наружу отдаётся только первая.
- **Версия WebKitGTK — только из Rust** (`webkit2gtk-sys`, уже в `Cargo.lock` транзитивно).
  Из JS недоступна: WebKitGTK репортит фиксированный Safari-compat `AppleWebKit/605.1.15`.

### Локализация системных сообщений — частично закрыта

Системные ошибки приходят в локали и уезжали бы в отчёт, предназначенный для публичной
issue (правило проекта: UI английский). Источники разные:

- **`std::io::Error` самого Sendoff** (спавн не состоялся) — локаль процесса. Закрыто:
  при статусе `not-found` причина не прикладывается вовсе, английская строка
  «Executable X not found in Sendoff PATH» говорит то же самое и точнее.
- **stderr дочернего процесса** — его локаль. Не чиним: в реальном сценарии провайдеры
  отвечают английским JSON-конвертом (проверено на Orca `runtime_unavailable`), русский
  текст появлялся только в искусственном прогоне с `PATH=/nonexistent`.

**`LC_ALL=C` дочерним процессам отклонён.** Технически возможен (`plugin-shell` принимает
`env` и добавляет его к унаследованному окружению, PATH не теряется), но `runScoped` —
общий путь и для ОТПРАВКИ, а `LC_ALL=C` переключает charset на ASCII: промпт с кириллицей
через `herdr agent prompt` рискует поехать битым. Менять критический путь отправки ради
косметики в диагностике — плохой размен. Если понадобится — только `C.UTF-8` и с
отдельной проверкой на реальной отправке.

**Остаточный случай, сознательно не закрыт:** отказ discovery с Rust-side ошибкой при
НАЙДЕННОМ бинаре (например, отказ прав на запуск) останется локализованным. Редко.

### Permissions

Добавлены две свои команды (`locate_executables`, `webkit_version`) — с явного
подтверждения автора. Обе не спавнят процессы: первая обходит PATH по списку имён,
**заданному в Rust**, а не приходящему из вебвью; вторая возвращает три числа из уже
загруженной библиотеки. Секции Application хватило существующих прав: `core:default`
включает `core:app:default` (версии, identifier) и `core:path:default` (`appLocalDataDir`).

## Сессия 2026-09-03 — webview XSS→RCE hardening

Найдена и закрыта потенциальная цепочка удалённого выполнения кода. Merge `d6a7637`.

### Уязвимость

Содержимое пользовательского таба шло в `marked.parse()` и **напрямую** в
`dangerouslySetInnerHTML` (markdown-preview, `Editor.tsx`). marked с v5 HTML не
санитизирует — их явная позиция. При `csp: null` и tmux с `args: true` складывалась
цепочка: чужой `.md` с `<img onerror>` / `<script>` → JS в webview → Tauri IPC
(`plugin:shell|execute`) → произвольный tmux subcommand (`run-shell`, либо `send-keys`
с любым текстом в чужую pane) → выполнение кода.

Ключевой момент: вся граница permissions (см. NEVER в `CLAUDE.md`) построена на
допущении «в webview исполняется только код Sendoff». XSS-sink это допущение снимает,
и тогда уже выданный `fs:scope-home-recursive` становится частью поверхности утечки —
**независимо от tmux**. То есть это не «баг в tmux», а брешь в самом фундаменте
threat-model'и. Отсюда — чинить в первую очередь, поверх YAGNI (правило само выносит
безопасность в исключение «не потом»).

### Фикс — три независимых слоя (defense-in-depth)

1. **Санитизация** (`Editor.tsx`, dep `dompurify`): `DOMPurify.sanitize()` на выходе
   `marked` перед вставкой. Нативный HTML Sanitizer API (`Element.setHTML`) **не
   годится**: наш единственный рантайм — WebKitGTK (Safari-семейство), который его не
   реализует; прогрессивное улучшение было бы веткой без жильца. Второй
   `dangerouslySetInnerHTML` (подсветка совпадений) — не sink: он гонит текст через
   `escapeHTML`, править не нужно.
2. **CSP** (`tauri.conf.json`): `csp: null` → `script-src 'self'` без `unsafe-inline`
   (глушит inline-обработчики независимо от санитайзера). Отдельный `devCsp` с
   послаблениями под Vite HMR (`unsafe-inline` + `ws://localhost:1420`). `style-src`
   оставлен `unsafe-inline` (React inline-стили до IPC не дотягиваются), `img-src` —
   `self data: blob:` (внешние `img` заблокированы: эксфил через tracking-pixel закрыт).
3. **Скоуп tmux** (`default.json` + `tmux.ts`): `args: true` → 4 именованных entry с
   валидаторами (`list-panes` / `set-buffer` / `paste-buffer` / `send-keys`). `send-keys`
   заперт на литерал `Enter` — набор произвольной команды в чужую pane убран. Приводит
   tmux к той же строгости, что `orca-ide` / `herdr`. Устраняет и молчаливое расхождение
   с ними.

### Проверка и её пределы

Статика зелёная (tsc / lint / 184 теста; манифест собирается; Rust компилируется).
Рантайм на изолированной инстанции (свой HOME, реальные данные не тронуты): под жёстким
прод-CSP приложение полностью рендерится, а пикер целей полон живых herdr/tmux-данных —
значит IPC/shell ходят сквозь `connect-src ipc:` (будь CSP кривой, список пуст). tmux
read-path под скоупом отработал (таргет появился), реальный `pane_id %0` матчит
валидатор write-path `^%[0-9]+$` — write-path закрыт по композиции.

**Изолировать отдельное срабатывание DOMPurify и атрибуцию PoC не удалось**, и это не
пробел в защите: (1) eval-канал `tauri-plugin-mcp-bridge` виснет на WebKitGTK, а wtype не
проставляет `KeyboardEvent.code` для хоткеев; (2) три слоя независимо дают «маркер не
создан», поэтому чёрный ящик на исправленной сборке в принципе не может сказать, какой
слой поймал. Каждый слой подтверждён отдельно. Детали инструментов — в Claude-memory
`reference_runtime_verify_tooling`.

## Отложенные идеи (не сейчас, требуют предусловий)

- **Chained Presets** + **Live Preview Transformation** — это пивот в pipeline-builder, ломает позиционирование «prompt-first editor». Включать только если появятся реально сложные пресеты и подтверждённая потребность.
- **API integrations (DeepL, spell check)** — ломают strict local-first. Если делать — только opt-in per-preset + API keys в Tauri secret store + обновление threat model в CLAUDE.md (сейчас «нет доступа к сети»).
- **ACP / MCP / agent-runner внутри Sendoff** (запуск Claude Code, Codex, Gemini CLI и т.п. с UI «Agent → Action → Source → Run → diff → Apply», как в Pencil.dev / Zed). **Не сейчас** по трём причинам: (1) ломает позиционирование «prompt-first editor» в сторону «agent-in-editor» — Cursor/Zed/Continue/Aider уже занимают эту нишу, Sendoff станет bad Cursor; (2) ломает threat model «no network, no processes» — потребует Tauri permissions на сеть/процессы, провайдер-абстракцию, секретный store для ключей, diff/cancel/retry; это второй продукт внутри Sendoff размером с сам Sendoff; (3) не решает текущий реальный pain «написать ответ затратно» — это решение для другой задачи (применить AI-трансформацию к тексту), которой у пользователя нет (prompt-шаблоны с `{{TEXT}}`-подстановкой выпилены 2026-06-30 как неиспользуемые; `Ctrl+K` теперь — trigger-phrases-пикер). **Условия включения:** появится конкретный кейс из реальных сессий, где «run agent inside Sendoff → diff → apply» явно выигрывает у текущего `Ctrl+Enter → Claude Code в tmux` flow. Зафиксировано как parked / future exploration, не как вечный отказ.
- **Context-mediator между tmux-агентами** (отдельный процесс/файл, собирающий контекст о проекте и инжектящий его в каждый агентский запуск). **Не сейчас:** knowledge-base direction (отказ в позиционировании), дублирует существующие `CLAUDE.md` / `AGENTS.md` (которые оба агента уже читают), требует filesystem access за пределы Sendoff. ## Известные ограничения

- **tmux-отправка в TUI с эвристикой «вставка vs ввод» (codex и подобные)** —
  требует `paste-buffer -p` (bracketed paste) + settle-задержку перед `send-keys
  Enter`, иначе приложение глотает Enter как часть пасты и сабмит не происходит
  (первый раз проходит по гонке, повторные виснут). Исправлено в `useTmuxSend`
  (2026-06-03). Claude Code / pi.dev работали и без `-p`.

- **Bulk-replace применяет пары последовательно, не single-pass.**
  `applyReplacePairs` / `previewReplacePairs` в `replaceEngine.ts` прогоняют каждую
  пару по кумулятивному результату, поэтому цепочки вида `А→Б`, затем `Б→В`
  срабатывают каскадом (double-replacement). Для тоновых пресетов (Вы→Мы) почти не
  стреляет. «Правильный» фикс — single-pass с объединённым regex, но у пар разные
  `caseSensitive`/`wholeWord`, в один паттерн не сливаются без возни. Сознательно
  оставлено как known limitation (отмечено внешним ревью, 2026-06-14).

- **Системная тема через `gsettings color-scheme` / nwg-look** — применяется только после рестарта приложения. Это ограничение WebKitGTK на Linux, не наш баг. Смена через GTK-вариант темы (например Graphite → Graphite-Dark) работает мгновенно. Пользователь явно выбрал не реализовывать D-Bus listener (вариант 1 «оставить как есть»).

- **Tearing/артефакты при скролле (WebKitGTK DMABUF-рендерер на Linux)** — на части
  GPU-драйверов (Nvidia, отдельные Mesa/Wayland) путь шаринга буферов DMA-BUF даёт
  разрывы и искажения при скролле. Не наш баг — особенность WebKitGTK. Запечено в
  `lib.rs`: на Linux выставляем `WEBKIT_DISABLE_DMABUF_RENDERER=1` до создания
  webview, если переменная не задана юзером (override сохранён). Аппаратный
  композитинг при этом остаётся. Если хирургического флага не хватает — кувалда
  `WEBKIT_DISABLE_COMPOSITING_MODE=1` (вырубает GPU-композитинг целиком). Это
  заменило ложную гипотезу «потолок textarea, нужен CodeMirror» — скролл-jank
  оказался багом платформы, а не редактора.
